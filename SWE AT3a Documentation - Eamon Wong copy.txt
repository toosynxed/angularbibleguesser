1.1 — Client Scenario (3 Marks)
Define a clear scenario based on the client’s needs, including the application’s purpose, target audience, and primary goals. Detail the client's requirements and provide a narrative that encapsulates the problem that the application aims to solve. Explain the overall vision and the expected impact of the application.

The initial Better Bible Guesser application was developed to provide people of faith to test their knowledge of the Bible, differentiating itself from market competition through the development of a multiplayer mode to allow users to test their knowledge of the Bible against others, encouraging scriptural-based conversations between people of faith and creating a community of encouragement and betterment of knowledge.

The current Better Bible Guesser application provides users with a easy-to-use interface that allows users to test their knowledge of the Bible through a range of guessing modes (including singleplayer 5-round mode, a daily mode, custom and sharable games and a multiplayer mode that allows other users to all play the same rounds at the same time and rank against others). Despite all these things Better Bible Guesser still lacks many functions and capabilities that could take the application to its maximum potential.

The current application, whilst functional, is not scalable and provides basic functionality with few customisation options, with initial loading times taking over 8 seconds, with the time taken for games to begin taking around 4 seconds. This is due to inefficient data management, requiring users to reload an entire 80,000 row .csv file every time. To improve this, the client requires that the new application should be able to support up to 1,000 concurrent user connections to the database, implement secure password encryption and storage methods, utilise best practise database transmission and security rules, better session management, and support offline capabilities. Additionally, aside from these essential functions, several other less important additions would be implemented, including an AI chat bot feature to assist with help topics but also to handle a new game mode that utilises videos and personalised content and a new and improved settings menu to allow for greater user accessibility among other small features.

With the implementation of these requirements, a more robust Bible guesser application will be able to support more users in their gospel learnings, fostering collaboration with secure and low-latency multiplayer modes, more detailed tracking of statistics, and personalisation to keep users engaged in learning and provide the best possible UX. The AI assistant will increase knowledge retention by making the user review already-guessed verses, and the experimental video mode will allow users to engage with the content in different formats.
Overall, the new version of Better Bible Guesser aims to produce an improved design of the application, introducing new features and capabilities to the game that will greatly improve user experience and retention for the application, aiming to be completed before Term 3, Week 1.

1.4 — Performance Criteria (3 Marks)
Specify the application's performance criteria, including speed, reliability, scalability, and user satisfaction benchmarks. Define how performance will be measured and the application's standards.


For the application to successfully reach the users satisfaction benchmarks, the speed of the application for loading must not be greater that 2 seconds for the initial loading time. Similarly, due to the introduction of a greater reliance on a Real-Time Database connection, communication times between the database and client must not exceed 200 milliseconds on a standardised internet connection (20MB/s upload and download speeds, 25 millisecond server ping).
The application must also demonstrate a 99.9% server and access uptime for school hours (8am until 4pm), to ensure that the application is available for use by schools. Similarly, the application must support capabilities for at least 1,000 concurrent users. The application will also utilise auto-scaling capabilities in order to automatically transition the data stores to a large-scale subscription plan if the volume and velocity of data transmissions exceed the current plan’s limits (Blaze plan currently provides support for a total of: 20,000 writes per day (5,000 per hour), 100,000 reads per day (10,000 per hour)), thus providing better performance for the web application. Similarly, if the application requires greater resources for a single server instance, FireStore Servers provide the capability for higher connection limits, and a greater server quality.
To provide the best user satisfaction experience for the client, the maximum number of clicks that will be required to join any game (whilst signed-in) will be 3 which will increase user satisfaction by reducing the complexities of navigating the application. Similarly, users will be prompted to rate their multiplayer-game experience out of 5 stars with a pop-up once they finish a multiplayer game. To successfully fulfill user satisfaction, the mean rating will need to be 4 or higher. Additionally, the application will utilise FireStore Authentication models to protect and secure password and other sensitive user information, thus improving the security of the application’s data storage.

Bitwise Operations
	•	Bitwise operations are a great way to store multiple Boolean values in one single numerical number. Bitwise uses a bit array to store multiple values in one single number by assigning individual variables powers of 2. Here is an example table of this:

For example, the setting for toggling dark mode on is set to the 7th bit number, and the setting for toggling on high contrast is the 4th bit number, if both were to be toggled on, you would add the 7th and 4th decimal value to the bitwise value (64 + 8 = 72). Using the bitwise operator AND (&), to check if the dark mode setting is toggled on (7th bit number), you would take the bitwise value and apply the AND operator with the decimal or power of 2 value for the 7th bit number (for example: 72 & 64) if the operation returns the decimal number inputted as the result, then the bitwise value does contain the bit number. However, if the operation returns 0 as the result, then the bit number is not present.

Using this method, it is possible to store multiple Boolean values (Such as the settings configurations for on/off features) all together in one variable, reducing the number of stored variables in the database. Additionally, Bitwise operations are usually up to several times faster than multiplication, significantly faster than division and even faster that addition and subtraction. Overall, using this system for both storage and processing of grouped Boolean values can be a great asset in developing a fast, lightweight and efficient software application. 
	•	Positives: Highly efficient and easy to code into software applications, allows for bundled variables reducing likelihood of data loss during transmission or processing as well as significantly reducing variable sizes for storage.
	•	Negatives: Can be difficult to understand the full capabilities for someone new, if stored Bitwise variables are not documented correctly there can be great confusion and time lost identifying and working backwards to identify the functions of even one Bitwise value.

Real-Time Databases
	•	Real-Time Databases (RTDB’s) provide the ability for a developer to synchronise and store data in “real-time” across multiple different applications and devices. RTDB tools also allow for automatic synchronisation of local changes made on a device while it was offline against remote changes, “Intelligently merging any conflicts” – Firebase. RTDB’s are also NoSQL-based databases, which means that it is optimised for fast and real-time functions and operations on a wide-large scale or global operation, rather than regional datasets. This means that it will be extremely useful in scenarios that require fast-paced and collaborative contributions from across the globe, or live-updates (for example, A multiplayer game or lobby).
	•	Positives: Offline data, conflict resolution, secure communication.
	•	Negatives: Not suited to regional datasets, difficult to upkeep and maintain individually.

Firebase Authentication
	•	Firebase provides an “Easy-To-Use” SDK (Software Development Kit) with pre-made UI’s that provide developers with controls to create authentication settings to protect their data within Firebase. Firebase supports popular authentication methods such as email and password, authentication via phone number, as well as many popular external providers such as Google, Facebook and X. This Firebase tool also has capabilities for “pro features” (with paid access) such as multi-factor authentication, user activity logging, blocking functions (such as IP blocks) and capabilities for SAML/OpenID Connect (SAML 2.0 and OIDC) support. There are two different methods supported by Firebase, SAML and OpenID Connect:
	•	SAML: Uses SAML 2.0.
	•	Positives: Very established, trusted and secure, very applicable for complex and important applications.
	•	Negatives: Resource heavy, complex.
	•	OpenID Connect (OIDC): Based on OAuth 2.0
	•	Positives: Much less resource-heavy than SAML, easier to use than SAML for simple applications.
	•	Negatives: A much newer method, not as many features than SAML.
	•	Overall, Firebase Authentication tools provide a very useful foundation to create secure systems for a web-based application.
	•	Positives: Secure, easy-to-use, simple interfaces.
	•	Negatives: Less customisation ability.

Cloud FireStore Databases
	•	FireBase supports cloud database connections and storage, a “Flexible and scalable NoSQL Database”, which organises data into collections of documents in a hierarchical format. This allows for Real-time connections, up-to-date information and recent and current data.
	•	Positives: Supports Firebase Authentication rules, scalable, easy-to-use and understand.
	•	Negatives: No SQL, not very customisable.


Relevant Best-Practises:
Security and Authentication Rules
	•	Firebase Password Policies: Allows for minimum and maximum length requirements, password requirement options (e.g. Requiring upper and lower case characters, requiring a numerical character, etc…). Also allows the user to enforce password policies for new accounts, rejecting invalid inputs, or accepting them.
Database Rules
	•	Read and Write permissions: Restrict who can edit and view specific data sets within the application to protect sensitive data and prevent unauthorised data changes.
Point-in-time recovery
	•	Protects data from accidental deletion or writes by providing the ability to version control and query previous versions of data for a certain time period, and allows you to selectively write the needed data back into the database.
Scheduled Backups
	•	Allows for automatic backups of your database to create timestamped data histories. This allows for version control and logging between time periods to identify when changes were made, and to completely roll-back to a certain timestamp if needed.

BEGIN RoundScoreCalculations (GuessedVerse, ActualVerseID)
	GET GuessedVerseID (GuessedVerse)
	GET ActualVerseIDComparison (ActualVerseID)
	SET VerseDistance to CALCULATE (ActualVerseID – GuessedVerseID)
//Here, the algorithm is using the inputted verse from the user and the actual verse ID that was randomly generated, and parses it through subprocesses to strip and expand out the ID’s and verse text into a comparable format.
	IF VerseDistance is less than 0 THEN
//Here, the algorithm checks to see if the difference between the guessed and actual verse ID’s are within the 100 point range, if not, then it gives no points, if it is, it calculates the rewarded amount of points.
		SET UserScore to 0
	ELSE 
		SET UserScore to 100 – VerseDistance
	ENDIF
	SET UserStars to 0
	IF GuessedVerse.booknumber is ActualVerseIDComparison.booknumber THEN
//Here, the algorithm retrieves the book number attribute from the Guessed Verse object created earlier, comparing to see if it is the same as the book number from the Actual Verse object, allocating one star if it is. 
		INCREMENT UserStars
	ENDIF
	
	IF GuessedVerse.ChapterNumber is ActualVerseIDComparison.ChapterNumber THEN
//Here, the algorithm is again checking for any possible star allocation by this time comparing the chapter numbers between the two objects, and allocating one star if they match.
		INCREMENT UserStars
	ENDIF
	IF GuessedVerse.VerseNumber is ActualVerseIDComparison.VerseNumber THEN
//Similarly, the same happens here, but with a star given if the verse numbers match correctly.
		INCREMENT UserStars
	ENDIF
	SET RoundResult to ResultObject (UserScore, UserStars)
	RETURN RoundResult
//Here, the algorithm then takes the generated score and stars and creates a round object with those attributes, which is then returned as an object. 
END RoundScoreCalculations (GuessedVerse, ActualVerseID)
BEGIN GuessedVerseID (GuessedVerse)
	SET VerseID to CALCULATE (GuessedVerse.booknumber * 100,000)
	SET VerseID to CALCULATE (VerseID + (GuessedVerse.ChapterNumber * 1,000))
	SET VerseID to CALCULATE (VerseID + GuessedVerse.VerseNumber)
//Here, what is happening is that the algorithm is creating the Guessed Verse ID for the inputted guessed verse. The algorithm first takes the book number inputted and multiplies that by 100,000 which produces a number with minimum 5 0’s afterwards. Next, the inputted chapter number is taken and multiplied by 1,000 meaning that this number will never exceed 99,999 and will always have 3 0’s afterwards. This gap allows for the two numbers just calculated to be added together. Next, the verse number is added to the value, completing the Verse ID generation for the guessed verse.
	RETURN VerseID
END GuessedVerseID (GuessedVerse)
BEGIN ActualVerseIDComparison (ActualVerseID)
	SET booknumber to CALCULATE (ActualVerseID / 100,000)
	SET chapternumber to CALCULATE ((ActualVerseID – (booknumber * 100,000))/ 1,000)
	SET versenumber to CALCULATE ((ActualVerseID – (booknumber * 100,000) – (chapternumber * 1,000))
//What is happening here, is that the algorithm is taking the verse ID of the actual verse which was randomly generated, and splits the number down into its 3 main components: Book number, chapter number and verse number. It does this by reversing the process taken to generate the verse ID for the guessed input.
	RETURN booknumber, chapternumber, versenumber
END ActualVerseIDComparison (ActualVerseID)
